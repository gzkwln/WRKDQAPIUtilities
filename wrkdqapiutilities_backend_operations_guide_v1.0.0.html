Redaction applied: plaintext secrets, credentials and project-specific SQL server details present in the source runbook are not reproduced.

1. Purpose and architecture

This guide consolidates the backend deployment and operating instructions for WRKDQAPIUtilities. It is intended for a technical user who understands SQL Server, PowerShell and SKP concepts but has not previously operated this solution.

Syniti APIs → GETAPIRESULTS / ApiResults → ImportJSONFile_* views → JSON_* tables → consumption views → Cloud Construct dashboard
Each execution can additionally archive raw/API and transformed data into *_History tables for trend reporting.

2. Prerequisites

Security: API usernames, API passwords, SQL usernames, SQL passwords, proxy credentials and project server addresses from the source documentation are deliberately omitted from this guide. Supply destination values through approved secrets/configuration handling. Do not hard-code production credentials into a reusable HTML or script.

3. Configure GETAPIRESULTS

GETAPIRESULTS is the central API configuration/result table. For the destination environment, populate or verify at least:

FieldPurposeDeployment action
ExtractIDLogical execution/configuration setUse the intended ID, e.g. TEST only where that convention is still valid.
TENANTIDDestination SKP tenant contextReplace source-environment value.
APIUsernameAPI credential identityUse the value provided for the destination.
APIPasswordAPI secretDo not document in plaintext.
URL / URLEXTENSIONEndpoint configurationValidate against the supported Syniti v3 API endpoints.
TABLENAME / TableOrder / ActiveProcessing metadataValidate before first execution.
If multiple extraction processes must coexist while retaining previous API results, use distinct ExtractID configurations rather than overwriting an active configuration.

4. Understand the transformation layer

  1. API payloads are stored as JSON in GETAPIRESULTS.GETRESULTS.
  2. ImportJSONFile_* views parse and expose JSON attributes as relational columns.
  3. webKnowledgeTierExtract_JSON_TABLES_Ins inserts the transformed rows into the corresponding JSON_* tables.
  4. Consumption views, with APIResults_Combined as an important starting point, combine the JSON tables and apply dashboard filtering/business logic.
  5. *_History tables retain execution snapshots used by weekly trend reporting.
API schema changes: if a new API version introduces fields required by the dashboard, update both the relevant ImportJSONFile_* parser view and the target JSON_* table (and history table where applicable).

5. Choose the execution model

A. Fully automated

Use when SQL CLR/API execution is approved and tested.

Schedule DQReportsGeneralData_Ins. The documented design runs the APIs for the configured extraction ID, transforms JSON into the JSON tables and saves history.

B. Semi-automated

Use when API calls cannot be made directly from SQL.

Run a PowerShell extraction on an approved server, insert raw payloads into ApiResults, and then execute the SQL archival/transformation steps.

6. Semi-automated weekly process

Step 6.1 — Clear staging data

USE [WRKDQAPIUtilities];
GO
DELETE FROM [dbo].[ApiResults];

Clear only the staging table before a new extraction. History tables are not cleared.

Step 6.2 — Run the API extraction

The source runbook calls Syniti v3 endpoints including rules, categories, data-quality-jobs, datastores, enforcements, implementations, subject-areas, systems and users. Pagination is followed until no new cursor is returned. The combined endpoint payload is inserted once per URL extension into ApiResults.

# SECURITY-SAFE TEMPLATE — populate through approved secret handling
$ApiUsername = '<API_USERNAME>'
$ApiPassword = '<API_PASSWORD>'
$SqlServer   = '<SQL_SERVER_OR_INSTANCE>'
$SqlUser     = '<SQL_USERNAME>'
$SqlPassword = '<SQL_PASSWORD>'

$pair = "$ApiUsername`:$ApiPassword"
$encoded = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair))
$headers = @{ Authorization = "Basic $encoded" }

$urls = @(
  'https://api.syniti.eu/v3/rules',
  'https://api.syniti.eu/v3/categories',
  'https://api.syniti.eu/v3/data-quality-jobs',
  'https://api.syniti.eu/v3/datastores',
  'https://api.syniti.eu/v3/enforcements',
  'https://api.syniti.eu/v3/implementations',
  'https://api.syniti.eu/v3/subject-areas',
  'https://api.syniti.eu/v3/systems',
  'https://api.syniti.eu/v3/users'
) | Select-Object -Unique

$connectionString = "Server=$SqlServer;Database=WRKDQAPIUtilities;User Id=$SqlUser;Password=$SqlPassword;"
$conn = New-Object System.Data.SqlClient.SqlConnection $connectionString
$conn.Open()

foreach ($url in $urls) {
  try {
    $urlExtension = ($url.TrimEnd('/')).Split('/')[-1]
    $nextUrl = $url
    $previousCursor = $null
    $allData = @()
    while ($nextUrl) {
      $response = Invoke-RestMethod -Uri $nextUrl -Headers $headers -Method GET
      if ($response.data) { $allData += $response.data }
      if (-not $response.cursor -or $response.cursor -eq $previousCursor) { break }
      $previousCursor = $response.cursor
      $nextUrl = $url + '?cursor=' + $response.cursor
    }
    $finalObject = [PSCustomObject]@{ data=$allData; cursor='' }
    $finalJson = $finalObject | ConvertTo-Json -Depth 10
    $cmd = $conn.CreateCommand()
    $cmd.CommandText = 'INSERT INTO ApiResults (URLExtension, JsonData) VALUES (@urlExt, @json)'
    $cmd.Parameters.Add('@urlExt',[System.Data.SqlDbType]::NVarChar,200).Value = $urlExtension
    $cmd.Parameters.Add('@json',[System.Data.SqlDbType]::NVarChar,-1).Value = $finalJson
    [void]$cmd.ExecuteNonQuery()
  } catch { Write-Host "Error with $url : $($_.Exception.Message)" }
}
$conn.Close()
The original Loop page contained plaintext API and SQL credentials and a project-specific SQL server address. They are redacted here. Rotate/revoke any credential that was exposed in plaintext if that has not already been done.

Step 6.3 — Archive raw ApiResults

INSERT INTO [dbo].[ApiResults_History]
    (URLExtension, JsonData, CreatedAt, WeekNumber, WeekYear, CapturedDate)
SELECT URLExtension, JsonData, CreatedAt,
       DATEPART(WEEK, CreatedAt), DATEPART(YEAR, CreatedAt), CAST(CreatedAt AS DATE)
FROM [dbo].[ApiResults];

Step 6.4 — Update GETAPIRESULTS

DECLARE @ExtractID nvarchar(50) = 'TEST';
UPDATE g
SET g.GETRESULTS = a.JsonData,
    g.LastUpdate = a.CreatedAt
FROM dbo.GETAPIRESULTS g
LEFT JOIN dbo.ApiResults a
  ON g.URLEXTENSION = a.URLExtension
WHERE g.ExtractID = @ExtractID;

Step 6.5 — Archive GETAPIRESULTS

INSERT INTO [dbo].[GETAPIRESULTS_History]
 (ExtractID, URL, URLEXTENSION, TENANTID, TABLENAME, GETRESULTS,
  APIUsername, APIPassword, APIPassword_BAK, TableOrder, Active,
  LastUpdate, WeekNumber, WeekYear, CapturedDate)
SELECT ExtractID, URL, URLEXTENSION, TENANTID, TABLENAME, GETRESULTS,
       APIUsername, APIPassword, APIPassword_BAK, TableOrder, Active,
       LastUpdate, DATEPART(WEEK, LastUpdate), DATEPART(YEAR, LastUpdate), CAST(GETDATE() AS DATE)
FROM dbo.GETAPIRESULTS g
WHERE NOT EXISTS (
 SELECT 1 FROM dbo.GETAPIRESULTS_History h
 WHERE h.ExtractID=g.ExtractID AND h.URLEXTENSION=g.URLEXTENSION
   AND h.WeekNumber=DATEPART(WEEK,g.LastUpdate)
   AND h.WeekYear=DATEPART(YEAR,g.LastUpdate));

7. Fully automated execution

After CLR/API execution has been approved and manual testing has succeeded, the source design identifies DQReportsGeneralData_Ins as the scheduler entry point for a complete run.

  1. Verify the intended ExtractID configuration in GETAPIRESULTS.
  2. Execute DQReportsGeneralData_Ins manually once in the destination environment.
  3. Validate API updates, JSON tables, consumption views and history.
  4. Only after successful validation, schedule the stored procedure using the approved SQL/enterprise scheduler.
  5. Capture run status and alert on failures.
Do not assume the source schedule should be reused. Frequency and execution window should match the destination project’s dashboard refresh requirement.

8. Proxy execution variant

When outbound API access requires a proxy, the Loop documentation specifies a separate proxy-capable assembly and a change to webKnowledgeTierExtract_GETAPIRESULTS_GETRESULTS_Upd.

  • Deploy/validate the proxy-compatible assembly.
  • Configure proxy server/domain/username/password through secure configuration rather than reusable documentation.
  • Use the proxy API routine (Syniti_API_Proxy) instead of the non-proxy routine (Syniti_API) in the execution stored procedure.
  • Retest a single endpoint before enabling the complete process.
